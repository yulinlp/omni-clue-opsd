## 1. 总览：Omni 模型怎么"看"和"听"

"Omni"指一个模型同时处理 **文本 + 图像 + 音频 + 视频**。核心思想只有一句话：

> **所有模态最终都会被编码成"token 序列"，拼在一起喂给同一个 LLM。**

```
图像 / 视频帧 ──► 视觉编码器 (ViT)  ──► 投影层 ─┐
音频 ─────────► 音频编码器 (Whisper 式) ──► ────┼──► 一串 token ──► LLM ──► 文本输出
文本 ─────────► 分词器 (tokenizer) ─────────────┘
```

由此推出三条工程直觉（本项目反复用到）：

| 直觉 | 含义 |
|---|---|
| **token 数决定一切** | 花多少钱、占多少显存、跑多慢，全看 token 数 |
| **预处理决定 token 数** | 分辨率、帧率、时长都是"预处理参数"，不是模型参数 |
| **模态可以取舍** | 不看画面时只给音频、不需要声音时静音视频，都能省钱 |

## 2. 图像 → token

### 2.1 机制：切块（patchify）+ 合并（merge）

主流视觉编码器（**ViT = Vision Transformer**，视觉 Transformer；把图片切成 patch 序列后送进标准 Transformer）把图片切成小块：

```
原图 640×360（= 宽 640 × 高 360，共 230,400 像素，16:9）
  │  切成 14×14 像素的小块 (patch)
  ▼
ceil(640/14) × ceil(360/14) = 46 × 26 = 1196 个 patch
  │  2×2 相邻 patch 合并成 1 个 token
  ▼
ceil(640/28) × ceil(360/28) = 23 × 13 = 299 个视觉 token
```

**记这个数：28×28 = 784 像素 → 1 个视觉 token**（Qwen-VL / Qwen-Omni 系列的典型值；不同模型可能是 14×14 或 16×16，看论文里的 "patch size" 和 "merge"）。

### 2.2 公式

```
视觉 token 数 ≈ ceil(高 / 28) × ceil(宽 / 28)
```

> 小贴士：也常用 "像素 ÷ 784" 估算：156800 px ≈ 200 token。

### 2.3 `max_pixels`：分辨率预算

Qwen 系模型用 `max_pixels` / `min_pixels` 控制"一张图最多/最少用多少像素"（保持宽高比缩放）：

| 配置值 | 含义 | 约等于 | 视觉 token/帧 |
|---|---|---|---|
| `min_pixels = 3136` | 最小 3136 px | 56×56 | ~4 |
| `full_scan_max_pixels = 31360` | 粗看用 | 236×133（对 16:9） | ~40 |
| `default_max_pixels = 156800` | 常规细看 | 528×297（对 16:9） | ~200 |
| `max_pixels_max = 313600` | 上限 | 747×420 | ~400 |

**规律：像素翻倍 → token 翻倍 → 成本/显存翻倍。** 但分辨率太低会看不清小字、远处物体——这就是"粗看 + 细看"两级策略的由来（见 §3.3）。

### 2.4 常见误区

- `max_pixels` 不是"宽"也不是"高"，而是 **整帧的总像素预算**；宽高比会被保留。
- 视频的每一帧都按这个预算算，**帧数会再乘一遍**（见下节）。

## 3. 视频 → token：采样（fps）是核心

### 3.1 视频 = 帧序列 + 时间轴

视频模型不会看"每一帧"（原始可能 30fps，1 分钟就 1800 帧）。它按 **fps（帧率）** 从时间轴上抽帧：

```
原视频 30 fps ──► 按 2 fps 采样 ──► 每 15 帧取 1 帧 ──► 1 分钟得到 120 帧
```

### 3.2 token 成本公式

```
视频 token ≈ 帧数 × 每帧视觉 token + 音频 token
帧数       = min(时长 × fps, 帧数上限)
```

本项目实例（一个 87 秒视频的全片粗看）：

```
帧数 = 87 × 2 = 174 帧（上限 600）
视觉 = 174 × 40 ≈ 7000 token
音频 = 87 秒 × 25 ≈ 2200 token
合计 ≈ 9200 token（一次 prefill）
```

### 3.3 本项目的多级采样策略（强烈推荐照抄）

| 用途 | fps | max_pixels | 帧数上限 | 每帧 token | 目的 |
|---|---|---|---|---|---|
| **全片粗看** survey | 2 | 31360 | 600 | ~40 | 便宜地建立时间轴印象 |
| **定点细看** inspect | 2–8 | 156800 | — | ~200 | 看清细节（字幕/动作） |
| **V1 自动验证** | 4 | 156800 | — | ~200 | 把证据区间单独喂给裁判模型 |

要点：
- **粗看用低分辨率高覆盖，细看用高分辨率小窗口**——总 token 反而更省，还看得更准。
- fps 决定**时间分辨率**：0.5 秒的动作在 2fps 下可能只出现 1 帧甚至漏掉；要抓快速事件就得提高 fps 或缩小窗口。

### 3.4 长视频的两个陷阱

1. **帧数上限**：我们的上限是 600 帧。482 秒的视频按 2fps 需要 964 帧 → 被截到 600 帧（时间分辨率下降到 1.24fps）。
2. **音频 token 反超视觉**：482 秒音频 = 12050 token，比 600 帧低清画面（24000 token）的一半还多。

## 4. 音频 → token

### 4.1 机制

音频先重采样到 **16 kHz 单声道**，送进 Whisper 式编码器，输出固定速率的 token：

```
音频 token ≈ 秒数 × 25
```

（25 token/秒是 Qwen-Omni / Qwen-Audio 系列的量级；具体看模型报告。）

### 4.2 对照表

| 时长 | 音频 token |
|---|---|
| 10 秒 | 250 |
| 1 分钟 | 1500 |
| 5 分钟 | 7500 |
| 8 分钟 | **12000** |
| 10 分钟 | 15000 |

### 4.3 本项目经验

- 一个 584 秒视频：音频 14600 token + 视觉（600 帧 × 40）24000 token ≈ **39000 token 的 prefill**，直接把 30B 模型显存打爆（OOM）。
- **模态选择很重要**：`av`（画面+声音）/ `video`（静音画面）/ `audio`（只要声音）。只看画面时用 `video` 能省掉全部音频 token。
- 音频是"线性成本"：时长翻倍，token 翻倍；没有"降采样"这种省法（重采样到更低采样率收益有限），**唯一有效的办法是截短时长**。

## 5. base64 是什么，为什么要用

### 5.1 一句话定义

base64 把**任意二进制数据**（图片/视频/音频的字节）编码成**只用 64 个可打印字符**（A–Z a–z 0–9 + /）的纯文本。

```
二进制: 11111101 00000001 10100100 ...   （人/JSON 都读不了，还可能有控制字符）
base64: /Q Gk ...                        （全是安全可打印字符）
```

### 5.2 为什么需要它

- HTTP / JSON 是**文本协议**，不能直接塞二进制字节（引号、换行、控制字符会破坏格式）。
- 云端 API（如 DashScope 的 OpenAI 兼容接口）接收的是一段 JSON；图片/视频必须以文本形式放进 JSON → 用 base64。
- 写法是 **data URI**：

```json
{"type": "video_url", "video_url": {"url": "data:video/mp4;base64,AAAAIGZ0eXBpc29t..."}}
```

### 5.3 体积代价：+33%（必须记住）

base64 用 4 个字符表示 3 个字节 → **体积变为原来的 4/3 ≈ 1.33 倍**。

| 原始文件 | base64 后 | 能否过 10MB 接口限制 |
|---|---|---|
| 7 MB | ≈ 9.33 MB | ✅ 刚好过 |
| 7.5 MB | 10.0 MB | ⚠️ 极限 |
| 10 MB | 13.3 MB | ❌ 超限 |

**本项目配置**：切片上限 7 MB（base64 后 9.33 MB < 10 MB 限制），这是"API 单条消息体积上限"倒推出来的参数。

### 5.4 工程含义

- base64 让 payload 变大 → 上传更慢、更贵 → **优先发"短片段"而不是"整段视频"**。
- 同一个片段被多题复用时要**缓存**（我们做了共享切片缓存 + 文件锁防并发写坏）。

## 6. ffmpeg / ffprobe 实用手册

ffmpeg 是多模态研究的"瑞士军刀"：抽帧、切片、转码、抽音频全靠它。`ffprobe` 是它的"体检工具"。

### 6.1 看文件信息（先 probe 再动手）

```bash
ffprobe -v error \
  -show_entries stream=codec_name,profile,pix_fmt,width,height,r_frame_rate,duration,bit_rate \
  -of default=noprint_wrappers=1 input.mp4
```

输出解读（本项目实例）：

```
codec_name=h264  profile=High  pix_fmt=yuv420p   ← 浏览器兼容的三大件
width=640  height=360  r_frame_rate=30/1          ← 分辨率与帧率
codec_name=aac  sample_rate=44100  channels=2     ← 音频
```

> **新手提示**：`pix_fmt=yuv420p` + `profile=High` + `h264` 是网页能播的"安全组合"；`yuv444p`、10bit、HEVC 在浏览器里经常放不了。

### 6.2 切片段（本项目最常用）

```bash
# 无损快切（-c copy 不重编码，秒级完成，推荐）
ffmpeg -ss 10 -to 20 -i input.mp4 -c copy out.mp4

# 重编码切片（要改分辨率/压体积时）
ffmpeg -ss 10 -to 20 -i input.mp4 \
  -c:v libx264 -preset veryfast -crf 28 \
  -c:a aac -b:a 64k \
  -movflags +faststart out.mp4
```

- `-ss` 放在 `-i` **前面**：快速定位（关键帧对齐）；放在后面：精确但慢。
- `-c copy`：只"搬家"不"重做"，画质无损、速度快；缺点是切点会对齐到关键帧（可能差几秒）。

### 6.3 缩放与压缩

```bash
-vf scale=-2:240          # 高度 240，宽度自动（-2 表示保持宽高比且为偶数）
-crf 28                   # 画质/体积旋钮：0~51，越小越清晰越大
                          #   18–23 ≈ 视觉无损；28–32 适合预览/传 API
-preset veryfast          # 编码速度/压缩率权衡：ultrafast → veryslow
-b:a 64k                  # 音频码率（语音 64k 足够）
```

### 6.4 faststart：网页播放的关键

MP4 的元数据（`moov` 原子）默认可能在文件**末尾**。浏览器要先拿到它才能播放，于是会发一个"取最后 N 字节"的请求（HTTP Range 后缀请求 `bytes=-65536`）。

```bash
ffmpeg -i in.mp4 -c copy -movflags +faststart out.mp4   # 把 moov 挪到文件头
```

> 我们真实踩的坑：服务器把 `bytes=-65536`（最后 64KB）错解成 `bytes=0-65536`（前 64KB）→ 浏览器永远拿不到 moov → 视频一直转圈。

### 6.5 其他常用

```bash
ffmpeg -i in.mp4 -vn out.wav        # 抽音频（-vn = no video）
ffmpeg -i in.mp4 -an out.mp4        # 去音频（-an = no audio）
ffmpeg -i in.mp4 -vf fps=2 frames/%06d.jpg   # 按 2fps 抽帧
ffmpeg -i in.mp4 -c copy -f null -  # 只做解码检查（查文件是否完整）
```

## 7. 工程实践：token 预算、显存与成本

### 7.1 预算表（本项目真实配置）

| 场景 | 帧数 | 视觉 token | 音频 token | 合计 |
|---|---|---|---|---|
| 87s 视频 · 粗看（2fps/31360px） | 174 | 7.0k | 2.2k | ~9k |
| 87s 视频 · 细看一个 15s 窗（4fps/156800px） | 60 | 12k | 0.4k | ~12k |
| 482s 视频 · 粗看（600 帧上限） | 600 | 24k | 12.1k | **~36k** |
| 584s 视频 · 粗看 | 600 | 24k | 14.6k | **~39k** |

### 7.2 显存：prefill 激活随序列长度增长

> **术语：prefill vs decode**
> LLM 推理分两阶段：**prefill**（读题）把整段输入一次性并行过模型、建立 KV cache、吐出第一个 token；**decode**（答题）再逐个生成输出 token。
> - prefill 是**算力密集**、峰值显存高（激活 ∝ 序列长度）、决定首字延迟（TTFT）；
> - decode 是**访存密集**（显存带宽瓶颈）、单步快。
> - 多模态场景里输入动辄几万 token，**OOM 和慢几乎都发生在 prefill**——所以要优化的是"输入长度"（帧数 × 每帧 token + 音频 token），而不是输出长度。

- 权重占显存是固定的（30B 模型 ≈ 60GB）；
- **激活值**随输入 token 数增长。本项目 OOM 现场：~48k token 的 prefill 需要一次性分配 ~13GB，加上权重后直接爆 80GB 卡。

### 7.3 降 token 的两把刀（血泪教训）

| 手段 | 效果 | 备注 |
|---|---|---|
| **减帧数** | token 线性下降 | 直接有效 |
| **降分辨率** | token 近似平方下降 | 更狠 |
| ⚠️ 只降 fps 不降帧数 | **完全没用** | 我们曾把 2fps 降到 1fps 想省显存——但 600 帧还是 600 帧，token 一点没少，继续 OOM |

### 7.4 成本控制（API 场景）

- **输入 token 是主要成本**：本项目单题平均消耗 ≈ 3.7 次调用（1 次 caption + 2.7 轮对话）。
- **缓存是最大杠杆**：caption（时间戳描述）生成一次 ~100 秒/1 万字符，若每次重跑都重新生成，成本直接翻倍。我们修复了"跨进程缓存失效"后，全量运行省下约一半 caption 调用。
- **先压测再全量**：我们用 200 题 pilot 测出 32 并发 0 限流，再上全量 3172 题，避免中途限流返工。

### 7.5 采样与"可复现性"

同一道题、同样的输入，**两次运行可能给出完全不同的证据区间**（本项目实测：169 道重复题中 155 道两次结果不同）。这不是 bug，而是生成式模型采样（temperature）的固有特性。

对策：
- 关键标注做 **2–3 次采样 + 多数投票**，或用自动验证器（V1）选优；
- 报告结果时注明"单次采样"还是"多次投票"。

## 8. 速查表

### 公式

```
视觉 token / 帧  ≈ ceil(高/28) × ceil(宽/28)     （Qwen-VL/Omni 系，28×28 px = 1 token）
视觉 token / 帧  ≈ 像素数 / 784
视频 token      ≈ 帧数 × 每帧 token + 时长 × 25
帧数            = min(时长 × fps, 帧数上限)
base64 体积     ≈ 原始体积 × 4/3（+33%）
```

### 数字

| 项 | 值 |
|---|---|
| 视觉 patch/merge | 14×14 patch，2×2 merge → 28×28 px/token |
| 音频 token 速率 | ~25 token/秒（16kHz 输入） |
| base64 膨胀 | +33%（7MB → 9.33MB） |
| 本项目像素档位 | 3136 / 31360 / 156800 / 313600 |
| 本项目 fps 档位 | 全片 2fps；细看 2–8fps；验证 4fps |
| 单条 API 消息上限 | 10MB（base64 后）→ 切片限 7MB |

### 常用命令

```bash
ffprobe ... input.mp4                              # 体检
ffmpeg -ss A -to B -i in.mp4 -c copy out.mp4       # 无损切片
ffmpeg -i in.mp4 -c:v libx264 -crf 28 -c:a aac -b:a 64k -movflags +faststart out.mp4   # 压片
ffmpeg -i in.mp4 -vf scale=-2:240 out.mp4          # 缩放
```

## 9. 本项目踩过的坑（新手最容易中招）

1. **只降 fps 不减帧数** → 显存没省下来（token 由帧数决定）。
2. **忽略音频 token** → 长视频 OOM 的隐形元凶（8 分钟 = 1.2 万 token）。
3. **base64 膨胀算漏** → 7MB 变 9.33MB，稍不注意就超 10MB 接口上限。
4. **MP4 的 moov 在文件尾** → 网页播放器一直转圈（要用 `+faststart`，服务器还要正确支持 Range 后缀请求）。
5. **分片文件重叠** → 同一题被标注 2–3 次，浪费一半预算（启动前务必校验分片两两不重叠、且与数据集完全对齐）。
6. **缓存跨进程失效** → 多进程并发时各自重新生成 caption，成本翻倍（用 mtime+size 检测文件变化）。
7. **单次采样不可复现** → 同一题两次结果差异大，关键结论要多次采样投票。
8. **浏览器兼容性** → 只认 H.264(High, yuv420p) + AAC；转码前先 ffprobe 确认。
