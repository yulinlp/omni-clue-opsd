## 0. 一分钟看懂

我们做两件事：

1. **标注（找证据）**：让一个多模态大模型（Qwen3-Omni-30B）看视频，
   输出"回答这道题需要看/听视频的哪几段"，例如 `180.0–185.0 秒`。
2. **V1 验证（查证据够不够）**：把刚才找到的那一小段单独剪出来，
   再问同一个模型："只看这一小段，你能答对这道题吗？"
   能答对 → 这段证据合格；答不对 → 不合格。

最终只保留"合格"的题目，用来做后面的 OPSD 训练（让 teacher 带着这段
特权信息去教 student）。

---

## 1. 为什么要标注证据区间

我们的研究叫 CLUE-OPSD：**student 看完整视频，teacher 只看关键证据片段**，
然后 teacher 把自己"看到证据后的判断"蒸馏给 student。

- OmniVideo-100K 数据集自带"证据时间段"标注（叫 `designated_segments`），
  所以之前能直接训练；
- **WorldSense 没有这个标注**，只有视频、题目、选项和答案；
- 所以我们要自己"造"证据时间段。

一个真实例子（视频 `FnOIAada`，24 秒）：

> 题目：视频开头红色赛车尾翼上的数字是多少？
> 选项：A. 56　B. 50　C. 58　D. 59
> 正确答案：B
> 我们标出的证据区间：**4.0–8.0 秒**（这段画面里能看到尾翼上的"50"）

## 3. 第一阶段：标注（证据定位 agent）

### 3.1 核心难点：模型其实"看不到"视频

大模型不是人，它没法自己拖动进度条。它每次只能看到我们**喂给它的东西**。
而"喂什么"（哪一段、多少帧、多清晰、要不要听声音）是**调用参数**，
写在提示词里没用——模型只看到已经被处理成数字的输入。

**所以我们换了个思路：让模型"点播"。**
它先说"我想看第 30 到 40 秒、每秒 4 帧、高清晰度、要声音"，
我们的程序按它的要求把这段剪出来喂给它，它看完再决定下一步。

### 3.2 实现方式：tool-loop（工具循环）

这就是所谓的"agent + 工具循环"：模型每轮只输出**一个 JSON**，
程序解析后执行动作，再把结果（或媒体）喂回去，如此循环。

**重要（2026-09-22 改动）**：模型**不能**跳过"看全片"这一步。
每道题开始时，程序会**强制**先把完整视频按 2 fps（若显存不足自动降到 1 fps）
连同声音喂给模型，让它先建立大致时间线，然后才允许它选择细看哪一段。

```
        ┌──────────────────────────────────────────────────┐
        │ 0. 程序强制先喂：完整视频 @2fps（含声音）          │
        │    → 模型输出"我看到的时间线"（第一次 observation）│
        └──────────────────────────────────────────────────┘
                          │
                          ▼
        ┌──────────────────────────────────────────────────┐
        │ 1. 程序给模型：题目 + 选项 + 视频信息 + 规则       │
        └──────────────────────────────────────────────────┘
                          │
                          ▼
        ┌──────────────────────────────────────────────────┐
        │ 2. 模型输出一个 JSON（例如"我要看 30-40 秒"）      │
        └──────────────────────────────────────────────────┘
                          │
                          ▼
        ┌──────────────────────────────────────────────────┐
        │ 3. 我们的程序按参数剪出这一段，喂回给模型          │
        └──────────────────────────────────────────────────┘
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
   还想再看 → 回到第 2 步      觉得够了 → 输出 submit（最终区间）
```

> 为什么强制先看全片？早期版本把数据集的**文字梗概**（video_caption）放进提示词，
> 结果 75% 的题第一轮就直接"猜"时间点（因为梗概是按时间顺序写的，模型会
> 把"梗概里靠后的事件"换算成"视频里靠后的时间"），容易猜偏且缺乏核验。
> 现在改成：**先看完整视频（不依赖任何文字描述）→ 再决定细看哪里**。

### 3.3 模型能做的三个动作

模型每轮必须输出**一个** JSON，只能从下面三种里选一个：

| 动作 | 作用 | 关键参数 |
|---|---|---|
| `inspect` | 点播一段视频（可带/不带声音） | `start`、`end`（秒）、`fps`（每秒抽几帧）、`max_pixels`（清晰度）、`modality`（看什么）、`focus`（这段要看什么） |
| `get_media_info` | 问视频的元信息（时长/帧率/有没有声音） | 无 |
| `submit` | 提交最终答案：证据区间 + 理由 | `intervals`（每段带 `observation` 理由）、`confidence` |

`modality` 有三种取值：

- `av`：同时看画面 + 听声音（最常用）
- `video`：只看画面，不听声音（比如空间关系题）
- `audio`：只听声音，不看画面（比如"观众什么时候欢呼"）

**每个动作都必须带 `observation` 字段**——也就是"我为什么这么做、
我看到了什么"。这是让模型"说出推理"的关键，也方便我们人工检查。

### 3.4 给模型的"题面"里放了什么

为了让模型更容易定位，我们把数据集里所有有用的信息都写进提示词：

| 字段 | 例子 | 作用 |
|---|---|---|
| `video_duration_seconds` | 212.04 | 告诉模型视频多长，避免它给出超范围的秒数 |
| `domain` / `sub_category` | Performance / Talks | 视频大类，帮助理解场景 |
| `audio_class` | ["Speech", "Event"] | 有没有人说话、有没有音乐/事件声音 → 决定要不要听声音 |
| `task_domain` / `task_type` | Recognition / Object Counting | 题目类型 → 决定用什么策略 |
| `question` / `options` | 题目和四个选项 | 要回答什么 |
| 规则 | 见下 | 区间必须 ≥1 秒、最多 4 段、总长不超预算、**不能说出答案** |

> **不再使用视频梗概**：数据集自带的 `video_synopsis`（文字描述）默认
> **不再放进提示词**（`--include-synopsis` 可打开，仅用于对照实验）。
> 模型必须通过"看视频"来定位，而不是"读描述"。

另外还有一段"按题型给的策略提示"和"工作步骤"，例如：

- **先看全片**：在第一次 `observation` 里描述你看到的时间线（开头/中间/结尾
  各发生了什么，哪些部分可能相关）；
- **再细看**：用 `inspect` 对最可能的区间提高帧率/清晰度确认边界；
- 时间定位/事件排序题 → 用多个短窗口、fps 2–4；
- 文字/图表题 → 提高清晰度（max_pixels ≥ 156800）；
- 音频识别/音源定位题 → 用 `audio` 或 `av` 模式去"听"；
- 若全片扫描是低帧率（长视频），时间估计只是近似的，提交前要放宽或平移窗口。

### 3.5 一个真实的完整回合

> 说明：下面这个例子来自**改动前**的运行（当时还依赖文字梗概），
> 保留它是为了说明"模型第一轮为什么能报出时间点"——它是根据梗概**猜**的。
> 改动后，模型第一轮必须先看完整视频并描述时间线，然后才决定细看哪里。

下面是题目 `NBzSgbJK::task0`（"视频里提到了几个国家？"，正确 4 个）
改动前的实际运行记录，一共 2 轮、耗时 30.4 秒：

**第 1 轮**，模型输出（注意它引用的是梗概）：

```json
{
  "observation": "题目问提到了几个国家。视频梗概里提到画了 BRITAIN、GERMANY、AMERICA、FRANCE 这些书……",
  "action": "inspect",
  "start": 180.0, "end": 185.0,
  "fps": 2.0, "max_pixels": 156800,
  "modality": "av",
  "focus": "书被画出来并被念出名字的那一段"
}
```

**它为什么能"猜"到 180–185 秒？**
因为梗概是按时间顺序写的：四个国家出现在梗概的第 70% 位置，
视频长 212 秒 → 模型推测"大概在视频后段"，就猜了 180–185 秒（85% 位置）。
这不是"知道"，而是"有根据的猜测"，所以它自己说的是 "To verify, I will inspect"。

**第 2 轮**，程序把 180–185 秒这段（带声音）喂给模型，模型看完后输出：

```json
{
  "observation": "白板上画了 BRITAIN、GERMANY、AMERICA、FRANCE 四本书，讲者同时说……",
  "action": "submit",
  "intervals": [{
    "start": 180.0, "end": 185.0,
    "observation": "这段画面里画出并念出了四个国家的名字"
  }],
  "confidence": 0.9
}
```

程序检查：区间合法 → **接受**。

**这个例子后来被 V1 判为"不通过"**（teacher 只给这段时选了 D，而正确答案是 C）。
这说明两件事：① 梗概猜测可能偏；② 即使定位大致正确，teacher 也可能答错
（后面 7.3 节的全视频对照实验证明 teacher 能力是主要瓶颈）。
这也正是我们要**去掉梗概依赖、强制先看全片**的原因。

### 3.6 规则和预算（防止模型乱来）

| 规则 | 数值 | 原因 |
|---|---|---|
| 最少轮数/最多轮数 | 最多 6 轮 | 控制成本 |
| 最多点播次数 | 3 次 | 防止反复看 |
| 每段区间最短 | 1.0 秒 | 保证抽帧后至少有 2 帧 |
| 单次点播最长 | 60 秒 | 防止一次喂太多导致显存爆掉 |
| 区间段数 | 最多 4 段 | 与训练数据格式对齐 |
| 总时长预算 | 不超过 min(90 秒, 视频的 50%) | 防止"把整个视频都当证据" |
| 不能做的事 | 说出答案 / 说出正确选项 | 保证定位过程不"偷看"答案 |

如果模型违规（比如区间太短），程序会**拒绝**并告诉它原因，让它重试。

### 3.7 模型真的会"自适应"吗？看真实统计

会。我们统计了 3172 道题里的 5775 次点播：

| 采样率 fps | 占比 | | 清晰度 max_pixels | 占比 |
|---|---|---|---|---|
| 0.5 | 3.6% | | 3136（很低清） | 11.4% |
| 1.0 | 5.5% | | 31360 | 3.8% |
| **2.0** | **66.1%** | | **156800（标准）** | **71.5%** |
| 4.0 | 24.7% | | 313600（高清） | 13.3% |
| 8.0 | 0.1% | | | |

| 看的模态 | 占比 |
|---|---|
| `av`（画面+声音） | 78.4% |
| `audio`（只听） | 12.1% |
| `video`（只看） | 9.6% |

而且它按题型调整：**音频题**平均 fps 只有 1.33–1.67（少抽帧、重点听声音）；
**动作计数/人机交互题**平均 fps 2.95–2.99（动作快，要多抽帧）；
**文字题**有 13% 会主动要求 313600 高清。

## 4. 第二阶段：V1 充分性验证

### 4.1 核心思想

> 如果**只给这一段证据**，模型能不能答对题？

- 能答对 → 这段证据是"充分的"（sufficient），可以用；
- 答不对 → 这段证据不够，这道题先不用。

这就是"充分性验证"（V1）。注意：**验证时仍然不给答案**，
答案只用来事后判分。

### 4.2 喂给 teacher 的输入长什么样

以 `FnOIAada` 的 `4.0–8.0 秒` 为例，实际输入是：

```
[系统提示] 你只能用下面这一小段视频（含同步声音）回答多选题。
          不要用外部知识，只回一个选项字母。

[媒体]     同一个视频文件，但只取 4.0–8.0 秒，带声音，
          每秒 2 帧，清晰度 313600（文字题自动提高）

[问题]     题目：视频开头红色赛车尾翼上的数字是多少？
          选项：A. 56.  B. 50.  C. 58.  D. 59.
          题型：Text and Diagram Understanding
          正确选项字母是：          ← 让模型直接接一个字母
```

**正确答案 B 不出现在输入里。**

### 4.3 怎么算"答对"和"有多确定"

模型用"贪心"方式生成（每次选概率最大的词），我们做两件事：

1. **取它生成的第一个字母**，和正确答案比 → `correct`（对/错）；
2. **取生成第一个词时的概率分布**（模型对词表里每个词的打分），
   只看 A/B/C/D 四个字母的分数，归一化成概率 → 得到：

| 指标 | 含义 | 怎么理解 |
|---|---|---|
| `probabilities` | A/B/C/D 各自的概率 | 例如 `{A:0.08, B:0.24, C:0.03, D:0.65}` |
| `p_true` | 正确答案的概率 | 0.65 表示模型认为正确答案的可能性 65% |
| `p_max` | 最高概率 | 这里 0.65 |
| `margin` | p_true 减去"其他选项最高概率" | 越大说明模型越"笃定且正确" |
| `entropy` | 概率分布的熵 | 越小说明越不犹豫 |

**两个真实例子：**

```json
// 通过（答对）：AJHiXSlt（情绪变化题，区间 110–115 秒）
{"gold":"D","answer":"D","correct":true,
 "probabilities":{"A":0.078,"B":0.240,"C":0.029,"D":0.653},
 "p_true":0.653,"margin":0.413,"entropy":0.922}

// 未通过（答错）：KbVeuqQH（音频识别题，区间 0–15 秒）
{"gold":"C","answer":"D","correct":false,
 "probabilities":{"A":0.001,"B":0.000,"C":0.009,"D":0.990},
 "p_true":0.009,"margin":-0.982,"entropy":0.059}
```

第二个例子很典型：模型非常"自信"地选了 D（概率 0.99），但答案是 C——
说明这段证据让它"听错/看错了"，不能用于训练。

### 4.4 输出长什么样

每道题一行（JSON），包含：题目信息、每个区间的对错与概率、
以及"最佳区间"（在答对的区间里挑概率最高的）：

```json
{
  "question_id": "AJHiXSlt::task0",
  "task_type": "Emotion Change",
  "gold_letter": "D",
  "n_intervals": 1,
  "any_correct": true,
  "n_correct": 1,
  "results": [ { "...单个区间的详细结果..." } ],
  "best_interval": {"start": 110.0, "end": 115.0},
  "best_p_true": 0.653,
  "verifier": {"fps": 2.0, "max_pixels": 156800, "modality": "av", "letters": ["A","B","C","D"]}
}
```

## 5. 代码在哪些文件里

所有代码都在 `src/omni_opsd/worldsense/` 和 `scripts/` 下：

| 文件 | 作用（一句话） |
|---|---|
| `src/.../worldsense/schema.py` | 定义"一道题"的数据结构 |
| `src/.../worldsense/config.py` | 各种上限：轮数、点播次数、fps、清晰度…… |
| `src/.../worldsense/media.py` | 探测视频信息（时长、帧率、有没有声音），带缓存 |
| `src/.../worldsense/dataset.py` | 读 WorldSense 的 JSON，拆成 3172 道题 |
| `src/.../worldsense/prompts.py` | 拼提示词（元数据 + 规则 + 按题型策略） |
| `src/.../worldsense/protocol.py` | 解析模型输出的 JSON（容错：带代码块、带废话也能解析） |
| `src/.../worldsense/views.py` | 把"点播参数"变成模型能吃的媒体格式（含音频处理） |
| `src/.../worldsense/clients.py` | 真正调用模型：加载 Qwen3-Omni、生成、取概率 |
| `src/.../worldsense/episode.py` | **核心循环**：一个题目的完整 tool-loop |
| `src/.../worldsense/runner.py` | 批量跑、断点续跑、写日志 |
| `src/.../worldsense/verify.py` | **V1 验证核心**：只给区间提问、判分、算概率 |
| `scripts/annotate_worldsense_evidence.py` | 标注命令行入口 |
| `scripts/verify_worldsense_evidence.py` | V1 验证命令行入口 |
| `scripts/worldsense_pipeline_monitor.py` | 每 30 分钟检查进度、自动重启的监控程序 |
| `tests/test_worldsense_agent.py` / `test_worldsense_verify.py` | 单元测试（不需要 GPU 就能跑） |

## 7. 实际跑出来的结果

### 7.1 标注阶段（3172 道题，8 卡，4.6 小时）

| 指标 | 结果 |
|---|---|
| 成功给出证据区间 | **2833 题（89.3%）** |
| 判定"没有证据"（no_evidence） | 248 题（7.8%） |
| 用尽轮数（budget_exhausted） | 91 题（2.9%） |
| 平均每道题几个区间 | 1.25 个 |
| 区间长度 | 中位数 5 秒（最短 1 秒，最长 78 秒） |
| 平均轮数 | 3.13 轮（46% 的题只用 2 轮：看一次就提交） |
| 平均点播次数 | 1.82 次 |
| JSON 格式错误 | 只有 10 题（0.3%） |

### 7.2 V1 验证阶段（18 分钟）

| 指标 | 结果 |
|---|---|
| 至少一段证据能答对（充分） | **1172 题 = 41.4%** |
| 单段证据的准确率 | 37.3%（1323/3546 段） |
| 通过证据的 p_true 中位数 | **0.930**（通过时通常很笃定） |
| 通过证据的 margin 均值 | 0.733 |

分题型看，**音频类题目表现最好**（音频识别 0.65、事件排序 0.51），
**计数类最差**（动作计数 0.21、物体计数 0.22）。

### 7.3 一个重要的诊断实验

41.4% 看起来不高，我们想知道：**是"没找对证据"，还是"模型本身不会答"？**

于是我们做了个对照实验：把 400 道**没通过**的题，直接给模型**完整视频**，
看它能答对多少。结果是：

```
完整视频也答不对的比例：71.2%
完整视频能答对（说明是定位问题）：28.7%
```

**结论：主要瓶颈是模型自身的能力上限，不是我们的定位质量。**
所以 41.4% 已经接近这个模型在 WorldSense 上的实际水平；
剩下能救回的约 29%，可以通过"把区间前后各扩 3 秒""多段联合验证"
等方法再提升。

## 8. 常见问题（FAQ）

**Q1：音频真的传进去了吗？会不会像之前 vLLM 那样把声音丢了？**
传进去了，我们做了三层验证：
1. 代码只用 Transformers 路径（完全没启用 vLLM，那个丢音频的坑不存在）；
2. 运行日志里有 12,250 次（标注）+ 7,092 次（V1）音频解码记录，0 次丢音频标记；
3. 用真实数据重放检查：`av` 点播会生成 `(1,128,500)` 的音频特征，
   `audio` 点播生成 `(1,128,400)`，且数值非零（不是静音）。
   另外，模型在 `UYkFSXsh` 那道题里说"这段没有听到欢呼声"——
   它能判断"没听到"，说明它确实在听。

**Q2：为什么有的题会说"没有证据"？**
模型看了 2–3 段后觉得找不到关键画面/声音，就会主动放弃（no_evidence）。
这类题我们直接跳过，不放进训练集。

**Q3：为什么大多数题只用 2 轮？**
因为很多题（如空间关系、属性识别）看一眼就够。统计上 46.4% 的题是
"看一次 → 提交"，只有 31.6% 的题用满 3 次点播。

**Q4：41.4% 是不是说明标注做得很差？**
不是。对照实验显示，那些没通过的题里有 71% 即使给完整视频模型也答不对。
换句话说，是题目本身对 30B 模型太难，不是证据找得不对。
而且 41.4% 是"只用一段证据"的严格标准，后续融合多段还能提高。

**Q5：模型能自己决定"看哪段、多清晰、要不要听"吗？**
能——但不是靠提示词里写"请用 2 帧每秒"。它必须输出结构化参数
（`start/end/fps/max_pixels/modality`），由我们的程序按参数去剪视频。
这就是为什么要用"工具循环"而不是一句话让模型直接给答案。

**Q6：为什么要用两个阶段，不能一次搞定？**
因为"找证据"和"判断证据够不够"是两个不同任务。
先让模型大胆找（宁可多找），再严格验证（宁缺毋滥），
比让一个模型一次输出"我觉得这段够了"可靠得多。

**Q7：模型为什么能在第一轮就说出一个具体时间点？它又没看过视频。**
（改动前的版本）它是根据提示词里的**文字梗概**猜的：梗概按时间顺序写，
模型把"梗概里靠后的事件"换算成"视频里靠后的时间"。
实测 74.8% 的题第一轮都明确引用了梗概，这个猜测可能偏。

**改动后**：不再给梗概，改为**强制先看完整视频**（2 fps，显存不足自动降到 1 fps）。
模型第一轮必须基于自己看到的画面/声音描述时间线，然后才允许细看某一段。

**Q8：全片扫描用 2 fps 会不会显存不够？**
会做**自动降级**：如果第一次生成因为显存不足（CUDA out of memory）失败，
程序会自动把扫描的帧率从 2 fps 降到 1 fps 并重试一次，不需要人工干预。
另外扫描最多抽 300 帧（长视频也不会无限增长），并且扫描本身**不占用**
3 次 inspect 的额度。

## 9. 名词小词典

| 名词 | 简单解释 |
|---|---|
| **agent（智能体）** | 会"思考 → 行动 → 看结果 → 再思考"的程序，这里指 Qwen3-Omni |
| **tool-loop（工具循环）** | 模型说要做什么，程序去做，把结果还给模型，循环往复 |
| **teacher（教师模型）** | 训练时给 student 提供"标准答案分布"的模型 |
| **特权信息** | teacher 能看到、但 student 看不到的信息（这里是证据区间） |
| **证据区间** | 回答某道题所需要的关键视频时间段，如 180.0–185.0 秒 |
| **fps（帧率）** | 每秒从视频里抽几帧。2 fps = 每秒 2 张图 |
| **max_pixels（像素预算）** | 画面清晰度上限，越大越清楚但越占显存 |
| **modality（模态）** | 输入类型：av=画面+声音，video=只看，audio=只听 |
| **充分性（sufficiency）** | 只用这段证据，能不能答对题 |
| **p_true** | 模型给"正确答案"的概率 |
| **margin** | p_true 比"其他选项最高概率"高多少，越大越笃定 |
| **断点续跑** | 程序崩了重跑时，自动跳过已完成的部分 |
| **分片（shard）** | 把 3172 道题平均分成 8 份，每张 GPU 跑一份 |

## 12. 两种后端：本地 GPU 模型 / 云端 API

框架现在支持两种"模型后端"，**对上层 agent 逻辑完全透明**（同一套 prompt、
tool-loop、预算、自动修正）：

| | 本地后端（默认） | API 后端 |
|---|---|---|
| 模型 | `/share/home/ylhu/models/Qwen3-Omni-30B-A3B-Instruct` | `qwen3.8-omni-flash`（阿里云百炼） |
| 运行方式 | Transformers + GPU（`device_map=auto`） | OpenAI 兼容 Chat Completions |
| 视图渲染 | `qwen_omni_utils` 结构化描述符（`video_start/video_end/fps/max_pixels`） | **ffmpeg 切成小 clip** → base64 data URI |
| 需要 GPU | 是（每卡一个 worker） | **不需要**（可在登录节点跑） |
| 音频 | `use_audio_in_video=True`，自动同步 | `av` → 带音轨的 clip；`audio` → 单独 mp3 |
| 概率（V1 用） | 首步 logits 重归一化 | API `logprobs`（取 top-k 中的选项字母） |
| 启动 | `launch_formal_annotation.sh` | `launch_api_annotation.sh` |

### API 模式的关键约束与应对

| API 约束（见官方说明文档） | 代码里的应对 |
|---|---|
| 视频只能用公网 URL 或 base64，**base64 < 10 MB** | 每次视图用 ffmpeg 转码成小 clip（实测 128–420 KB），三级回退：降帧率 → 降 CRF → 降分辨率 |
| 视频时长 ≤ 2 小时 | 我们的视图最长 120 秒，无压力 |
| 单请求最多 64 个媒体文件 | 每次只发 1 个视图 |
| 视觉与音频分开计费 | clip 带缓存（相同视图只渲染/上传一次） |
| 支持多模态组合输入 | `av`/`audio`/`video` 三种 modality 分别映射到带音轨 clip / mp3 / 静音 clip |
| 支持 Function Calling | 与本地模式一致，仍是"模型给参数 → harness 渲染"的 tool-loop |

### 运行方式

```bash

# API 模式（无需 GPU，需先配置 API Key / Base URL）

export DASHSCOPE_BASE_URL="https://<workspace>.cn-beijing.maas.aliyuncs.com/compatible-mode/v1"
bash output/worldsense_agent_jobs/launch_api_annotation.sh   # 默认 8 个分片
```
