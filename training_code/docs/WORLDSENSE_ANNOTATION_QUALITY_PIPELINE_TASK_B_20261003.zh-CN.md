# WorldSense 标注质量调查与自动标注流程改进方案（任务 B）

日期：2026-10-03。调查对象：本项目交接的 Qwen3.8-Omni-Flash 标注，以及最近四项 observation/answer 训练使用的数据。

本文最初与重新评测并行完成，初稿仅调查现有数据和代码。此后按用户授权，已调用 Qwen3.8-Omni-Flash 完成前50题试跑及其中23题的新版重跑；运行结果另存，未覆盖现有训练数据或冻结评测标签。**最新结果、17条待复核题的统计、失败反馈和当前流程与历史 agentic 流程的区别，见第13节。**

## 1. 结论先读

当前可以确认，训练数据存在一些实质性的标注和加工问题。最直接的问题是：**证据定位阶段的 observation，被直接当作 SFT 的解题分析；它与标准答案之间没有充分的一致性检查。**部分样本真的出现了“分析说 22，答案说 28”“分析说逆时针，答案说顺时针”的冲突。

但不能因此把所有训练失败都归因于标注。

- CLUE 的“没有最终答案、长段循环”还涉及训练目标、学生生成前缀、EMA 教师反馈、停止行为、解码和多媒体输入条件。
- 不加 observation 的 CLUE 也出现了大量循环，所以 observation 不是全部原因。
- 旧开放式评分存在错判；本轮评测正在改正评分并统一推理条件，结果尚未全部完成。

用户记忆中的“标完没有核验就直接训练”，需要更精确地说：

> 本批 API 数据做过格式检查、媒体检查及 Full/Gold 自动效用筛选；项目也有旧本地标注的 V1 实验记录、少量人工抽检记录和人工审核网站代码。但是，现有交接产物和训练构建代码没有体现**覆盖本次 1,453 条训练样本的独立语义复核、人工终审及强制放行门禁**。

建议的改进顺序是：**先隔离文本冲突和不完整的开放题，再核对音视频事实和时段，最后重新筛选；不要为了凑 1.5k 条把未经确认的 observation 直接拼成训练答案。**

## 2. 三种“标签”必须分清

| 字段 | 来源 | 含义与局限 |
| --- | --- | --- |
| 原题、选项、正确选项字母 | WorldSense 原始 QA | 数据集参考答案。没有重新看音视频核验前，不能等同于本项目已经确认的真值。 |
| `clue_intervals` | API 标注模型 | 模型认为有证据的时间区间。本项目所谓 golden clue 是模型标注，不是逐条人工确认的黄金证据。 |
| `observation` | API 标注模型提交 `submit` 时的说明 | 混合了观察、定位理由、推断、选项比较和检查计划。它并不天然等于一段合格的解题分析。 |

当前训练又生成了 `gold_answer_text`：把原正确选项的**文字内容**取出来。这样做通常合理，但有例外：答案可能仍是事件代码，或者原问题本身依赖已经被删掉的选项。

因此，“标准答案和 observation 冲突”只能先证明**同一条训练监督内部不一致**。究竟 observation 错、原标签错，还是问题指代不清，需要检查原音视频。

## 4. 已确认的数据问题

### 4.1 分析和答案存在文本冲突

在 1,453 条训练样本中，规则抓到 35 条“observation 明确支持与标准答案不同的选项”候选。逐条阅读后的结果为：

| 助手文本复查结果 | 数量 | 解释 |
| --- | ---: | --- |
| 分析与最终答案直接冲突 | 23 | 对数字、人物、方向、状态或事件顺序给出不一致结论 |
| 分析自身内部的选项/事件映射冲突 | 2 | 分析前半段与 gold 一致，后半段却引用相反的事件或左右关系 |
| 条件性角色歧义 | 1 | 分析自己也承认题目或角色指代可能有误 |
| 分析不足以支持最终答案 | 1 | 承认没有相关证据，随后用猜测给出解释 |
| 部分相容或仍需视频确认 | 8 | 不能把选项字母不同直接当成语义互斥 |

**23+2 不是全训练集的完整错误数，也不是视频真值错误率。**这是对一种较窄文本规则抓到的候选的复查结果。未写 `matches option B` 等字样的冲突还可能被漏掉；例如原错误分析文档中的 `hFSjJhYE::task0` 和 `zetwUmDH::task0` 就不在这 35 条里。

这25条约占训练样本的1.72%，仅代表本次已发现的问题，不能单独解释旧CLUE评测中数百条重复和缺答案；它与优化目标、教师反馈和推理条件的交互作用仍需对照实验。

- 视频总长约 48.715 秒，最后可读的比分支持标准答案 **28 to 24**。

### 4.3 实例二：分析说“逆时针”，答案说“顺时针”

### 4.5 实例四：不是所有“不同选项”都真冲突

`oMbOCwOD::task3` 的分析提到先拍打、后喂零食；最后引用了较窄的“直接喂零食”选项。gold 是“轻拍几次然后喂零食”。这两种描述有重叠，分析本身也提到了轻拍，不能只因选项不同就判分析错误。

`zatkNppT::task0` 的分析说先击掌再拥抱；题目问第一个庆祝动作，gold 是击掌。这也可以相容。

因此，自动筛出冲突后仍需要语义复核：**不同表述、不同细节范围与逻辑矛盾不是一回事。**

### 4.6 定位 observation 的任务，与训练分析的任务不完全相同

标注 prompt 明确写着：只定位证据、不要回答、不要说哪个选项正确。可是产物中 440/3,118 条 submitted observation 仍有显式 `option/choice A-D` 引用，其中训练集有 192 条。

SFT 加工脚本把这 192 条的 `option B` 等引用替换成选项文字；这会把一句“matches option B”改成“matches the answer 某个内容”，**但不会检查那个内容是否等于真正的正确答案**。

此外，清洗后的训练分析仍有 109 条包含 `options/choices` 一类词，部分还保留 `A. ... B. ...` 列表；1,112 条含 `inspection/inspect/survey/caption/synopsis` 等来源用语。这些是文本风格统计，不能全部算成错标。不过，它们表明定位 agent 的过程说明没有经过充分改写，直接进入了“普通学生看完整视频回答”的监督。

这两个计数来自 `training_target_style_flags.json`，只检索 analysis 正文：109使用 `\b(?:options|choices)\b`；1,112使用 `\b(?:inspect(?:ed|ion)?|survey|caption|synopsis|reference\s+(?:text|observation|caption))\b`。`audit_summary.json` 中另有1,105条通用词命中，它检索完整target、包含option/choice/clue等词但不包含survey/synopsis，口径不同，不能混用。

例如，`BWlTtVQn::task1` 的长分析仍写“Wait, looking at the options again”“Let's re-examine the frames”，而学生 prompt 已经没有选项，也没有 inspect 工具。

来源：[标注要求](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/training_code/src/omni_opsd/worldsense/prompts.py:19)，[选项替换与直接拼接实现](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/training_code/scripts/prepare_worldsense_observation_sft.py:33)。

### 4.7 开放题转换没有处理完“答案是事件代码”的情况

1,453 条训练答案中有 **25 条**仍是 `(a)(b)(c)` 一类事件序号。

- 其中 24 条在问题中给出了事件与符号的对应关系。这是**题内事件标签**，不能混同于 A/B/C/D 选择题选项；语义可解释，但与“尽量使用完整自然语言提供密集监督”的实验目标仍有距离。
- `vwNurRWU::task0` 的问题没有 a/b/c/d 对应关系，最终答案却是 `(a) (b) (c) (d)`。

这条训练输入为：

```text
Question: What is the correct sequence of bond types and their
corresponding formulas mentioned by the woman in the video when
discussing cohesive energy?
```

分析其实已经写了：

```text
Ionic -> Coulomb interaction,
Covalent -> Morse potential,
Van der Waals -> Lennard-Jones potential,
Metallic -> many-body interaction.
```

但最终答案仍是没有映射的四个符号。这种目标不能让评测者可靠理解模型要答什么，也没有充分利用具体知识内容。本次还抽看了 48 秒的板书画面，内容确实涉及这些键型和相互作用；**缺符号映射的问题可直接从当前 prompt/target 确认，修订完整答案还需结合全段核验。**

来源：[实际训练目标，第 363 行](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/training_runs/worldsense_observation_sft_lora_20260930/data/sft_observation_openqa.jsonl:363)。

留出评测也有同类例子：`xpALqvCU::task1` 问饮食顺序，参考答案为 `eakdfbchg`，开放 prompt 却没有字母映射。该题未参与训练，应在独立 benchmark 问题登记中处理，不能悄悄改动正在进行的冻结评测标签。

### 4.8 caption 校验的确有逻辑缺口，但不要把误报全部算成坏描述

现有 `validate_caption()` 只要求至少 200 字符、至少两个匹配的时间段。它不检查内容是否正确，也不检查时间段顺序、完整覆盖、越界或音视频来源。

更具体的问题是，时间正则允许 `[00:00:000-00:15:000]` 等冒号毫秒写法，却不接受常见的 `[00:00:00.000-00:00:15.000]` 点号毫秒写法。

核对最终 submitted 的 trace：

| 项目 | submitted 中数量 | 训练集中数量 |
| --- | ---: | ---: |
| 最后一次 caption 被旧校验器标为不合格 | 448 | 228 |
| 最后一次 caption 截断 | 60 | 27 |
| 不合格或截断的并集 | 455 | 232 |
| 旧校验器标不合格，但扩展解析能读出至少两段时间 | 364 | 180 |

例如 `BnseaLEM::task0` 的 caption 使用了点号毫秒，实际有多个时间段，却被标为 `too_few_timestamps(0)`。

训练中有23条同时不合格且截断，所以并集为228+27−23=232，而不是两项直接相加；这里的不合格指旧校验器的判定，不代表语义不合格。

第二次生成仍不合格或截断时，API bootstrap 仍返回 `skip_survey=True` 并把 caption 交给规划，缺少明确“重新分块/回到 AV survey/转人工”的分流。

因此这里有**两项不同修复**：先让校验器兼容合理时间格式，避免浪费重试；再对真正不完整、截断或无可靠时间线的描述采取明确降级与隔离。后续 inspect 可能补偿问题，不能把上述 232 条直接标为错标。

来源：[旧 caption 校验](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/training_code/src/omni_opsd/worldsense/prompts.py:194)，[重试后仍进入规划](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/training_code/src/omni_opsd/worldsense/api_client.py:294)。

### 4.9 区间被自动改动后，没有重新验证对应事实

标注器会为减少预算耗尽而修剪、拆分、丢弃或扩展区间，这些操作有日志，并非完全无记录。

但修改后保留原 observation，再直接设为 submitted；没有要求模型重新看**最终实际保留的区间**并确认其仍能支撑全部事实。

统计中：

- 3,118 条 submitted 中，286 条有自动调整；其中 227 条涉及拆分、修剪、删除等实质调整，其余多为边界毫秒修正。
- 1,453 条训练中，116 条有调整；其中 **82 条**有实质调整。
- 候选构建再次清理区间后，训练中 30 条的区间列表与原标注不同；16 条只是排序变化，**14 条**涉及边界或区间变化。
- 训练中 **54 条**最终 clue 有超过 1 秒未被详细 inspect 覆盖。它们可能在全片 caption/survey 中被看过，这一计数反映局部复核不足，不能当作 54 条错标。

对计数、先后顺序、全片变化和“没有发生某事件”等题目，固定偏好短证据片段尤其需要谨慎：删掉一段可能删掉一个计数事件、最终状态，或者反证。

来源：[区间自动修复](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/training_code/src/omni_opsd/worldsense/episode.py:208)，[候选区间清理](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/screening_code/scripts/worldsense_gap/prepare_candidates.py:64)。

## 5. Full/Gold 筛选为什么没有挡住这些问题？

### 5.1 它回答的是“短片有没有帮助这个 7B 模型”，不是“全部标注是否正确”

筛选只把完整音视频和证据音视频分别送给冻结 Qwen2.5-Omni-7B，比较选项概率和对错。它不接收待训练的 observation，因此无法检查分析和答案是否一致。

最终训练集的筛选分布是：

| Tier | 数量 | 原筛选定义 |
| --- | ---: | --- |
| A | 279 | Full 错，Gold 对 |
| B | 393 | 两种视图对错不变，但正确选项概率增加至少 0.1 |
| D | 781 | 其余；此训练集没有 Tier C |

其中 **560/1,453（38.54%）**在 Full 和 Gold 下都答错：Tier B 166 条，Tier D 394 条。

Tier B 可以这样产生：

```text
Full：正确选项概率 0.10，另一选项概率更高，答错。
Gold：正确选项概率 0.25，仍有另一选项概率更高，还是答错。
差值 +0.15，因此属于 Tier B。
```

这个例子是说明定义的示意数字。它表明 **Tier B 不是“已确认高质量证据”**。

### 5.2 原选样先按增益排序，再取足量样本

代码排序键为 `Δacc → Δp → Δlogp → P(GT|Gold)`，加每视频最多 5 题，然后取前 N 条；没有“先经过语义验证并 accepted”的条件，也没有要求 `correct_gold=True`。

因此 `selected_1500` 中 Gold 答对 920 条、答错 580 条；去掉部分短帧样本后的实际训练数据中，Gold 答对 893 条、答错 560 条。

**不能直接删掉这 560 条并认定它们都错标。**7B 可能不会正确识别某些真实证据；反过来，Gold 答对也可能来自猜测，HuRReUbF 的例子还说明答对并不验证 observation。

建议把“质量判断”和“训练效用判断”分开保存：

```text
先确认：问题可答、事实可靠、分析与答案一致、证据有效。
再筛选：这个有效证据是否给 teacher 提供了优势。
```

不要用 Tier A/B/D 代替 `accepted/review/quarantine`，它们是不同维度。

来源：[Tier 与选样实现](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/screening_code/scripts/worldsense_gap/select_gap.py:50)。

### 5.3 自评 confidence 也不能充当复核

3,084 条 submitted 有 confidence；均值约 0.967，1,847 条直接给出 1.0。上述 560 条 Gold 答错的训练样本中，463 条 API 自评 ≥0.95，309 条自评 1.0。

这是两个不同模型、不同任务的结果，不能据此计算 API 真实校准误差；但它说明 `confidence=1.0` 不是足够的训练放行凭证。放行必须依赖独立检查，而不是模型自己说“我确定”。

## 6. 历史 Qwen3.8-Omni-Flash agentic 标注框架怎样工作？

```text

submit(intervals, observation, confidence)
       ↓ 自动修正一些区间
merged.evidence.jsonl + trace
```

### 6.3 音频是否完全没有核验？不是

当前代码确实有音轨检查：`clips.py` 对带音频转码结果调用 ffprobe，检查音轨、采样率、声道，缺音频则报错；audio-only 也有此检查。

这能防“切片没有音轨”，不能证明：

- 音频与视频对齐正确；
- 说话内容被正确听出；
- speaker 被认对；
- 计数没有遗漏；
- 模型真正利用了这个音频信号。

新流程应在现有技术检查之外增加**内容级听觉核验**，例如关键句的带时间 ASR、音乐/事件计数的逐段确认。不能从训练效果不好倒推出“音频一定没输入”。

### 6.4 请求分辨率、转码分辨率和云端实际采样是三件事

API 后端先尝试请求的尺寸/fps，再为了文件大小回退到低 fps、小尺寸、更强压缩。最终转码元数据被写在 clip 缓存旁边的 JSON 中，但交接 annotation 的 `media_views` 主要保存请求参数，不包含完整最终转码选择，也不等于云端模型最终用的帧列表。

改进时应把最终 clip 的哈希、实际尺寸、实际 fps、音轨、编码参数、文件大小与请求 ID 关联到每个事实。否则以后看到“请求了高清”，仍难判断模型真的获得了怎样的画面。

## 8. 这些问题怎样影响 SFT 和 CLUE？

### 8.1 对 SFT：它会认真拟合不一致的目标

SFT 学的是“下一个 token 应该是什么”。对 `analysis=22:24, answer=28:24`，训练仍同时要求模仿两种数字。把 observation 拉长，增加的是更多要拟合的文字；如果文字含猜测、过程计划或错误事实，监督密度增加不等于有效信息增加。

已完成训练中，LoRA SFT 各轮平均训练 loss 约 `1.850 → 1.542 → 1.483`，全参数 SFT 为 `1.507 → 0.763 → 0.370`。这说明目标文字更容易被拟合，但旧选择题正确率没有稳定提高。它们与标签问题相容，**尚未形成“修好标签就一定提高多少分”的因果证据**。

目标分词统计中，analysis 正文占完整目标 token 总量约 86.03%，answer 正文约 5.63%。这不是梯度贡献比例，但足以说明模型大量学习了分析表达；必须先审核这些表达是否可靠。

### 8.2 对带 observation 的 CLUE：额外文字也可能给出相互拉扯的条件

teacher 同时收到 clue、gold answer、observation。若 observation 说逆时针、gold answer 说顺时针，teacher 需要自行解决冲突，而数据层没有告诉它哪条事实已核实、哪条是假设。

teacher 又是在**学生已生成的前缀**上预测后续 token，不能简单回头改掉前缀里的错误分析。gold 和参考文字可帮助纠正，但并不保证它一定在每种错误前缀上形成强烈的纠错、结束分析和回答反馈。

因此“teacher prompt 加了黄金答案”不能替代可靠的观察事实和完整性检查。

### 8.3 对不带 observation 的 CLUE：clue 质量仍然有影响，但不解释全部循环

不带 observation 的实验没有直接接收错误观察文字，仍接收 API clue 和数据集答案；它也可能受到错区间、遗漏必要上下文和题目本身缺映射的影响。

不过它同样发生了大量重复，因此必须继续检查优化目标和生成反馈，不能用 observation 一项解释所有退化。

训练中保存的全部 4,320 条学生回答，严重长段重复仅为带 observation 7 条、不带 observation 4 条；旧贪婪留出评测第3轮则分别达到332/518和395/518。训练里更明确的趋势是回答变长、缺答案增多。这个差异提醒我们，**先完成当前推理条件统一的重新评测，再判断剩余问题及其归因**。

建议以后按下面的顺序处理：

```text
保留原始题目、答案和视频，建立新版本
                  ↓
把选择题改成可以独立理解的开放题
                  ↓
重新确认：什么时间，画面/声音里实际发生了什么
                  ↓
选出能支持回答的证据片段，检查最后实际保留的片段
                  ↓
让核验模型不看标准答案，自己看视频回答
再单独检查：每一条观察说明是否有画面/声音支持
                  ↓
核对证据、独立回答和数据集答案，有冲突就暂停这一题
                  ↓
用已确认的事实写简短分析，检查分析与答案是否一致
                  ↓
逐题自动审核 + 批次人工抽检 + 疑难题人工处理
                  ↓
合格题进入 Full/Gold 效用筛选，再导出 SFT/CLUE 数据
```

### 9.1 先解释几个会用到的词

| 词 | 用普通话解释 |
| --- | --- |
| gold / 标准答案 | WorldSense 文件里原本给出的参考答案。它需要与视频核对；文件写了gold不代表本项目已经逐条确认。 |
| observation / 观察说明 | 标注模型写的“我看见、听见了什么，以及为什么选这段”。现在里面有时混入猜测和选项比较。 |
| clue / 证据片段 | 从整段视频里选出的一段或几段时间。它们应该包含解题所需的信息。 |
| 独立回答，原先称“盲答” | 核验者先不看标准答案和旧说明，只根据视频自己回答。目的是减少“看到答案后照着解释”的影响。 |
| 事实核验 | 检查一句说明是否真的有画面或声音支持。例如“47.5秒比分22:24”是否可读。 |
| 一致性检查 | 检查分析和答案是否互相冲突。例如分析说逆时针，答案说顺时针。它不能代替看视频。 |
| 放行条件，原先称“门禁” | 程序规定：必要检查没有通过，这道题就不能写入正式训练文件。 |
| 来源清单，原先称“manifest” | 一张记录表，说明本批使用了哪些题、视频、代码版本和检查结果，方便以后查来源。 |

下文还会提到 ASR 和 OCR：**ASR 是把语音转成文字，OCR 是读出画面上的文字。**二者都可能识别错，只是辅助工具。

### 9.2 用一个真实比分题贯穿下面的步骤

样本是 `HuRReUbF::task1`，视频为 Texas/Maryland 美式橄榄球比赛。

| 当前材料 | 内容 |
| --- | --- |
| 问题 | 视频最后显示的比分是多少？ |
| 数据集答案 | 28 to 24. |
| 原观察说明 | 大约47～48秒看到22:24，把它当作最终比分。 |
| 原证据区间 | 46～48.715秒，已经覆盖视频末段。 |
| 本次实际抽帧发现 | 47.5秒为22:24；48.25～48.6秒已更新为28:24。 |

这道题不需要凭空换一个答案。需要做的是：确认比分更新，修正那段把旧比分当成最终比分的分析，再检查修订结果。

**下面用它展示“新流程将怎样处理”。示例文字是建议修订的讲义，不代表已经改写现有训练数据。**

### 9.3 第一步：把原材料保留下来，从新版本开始

**做什么。**保留原问题、选项、答案、视频和旧标注，在一个新的工作目录中开展修订。为每道题记住题目ID，例如 `HuRReUbF::task1`，避免不同文件里的材料配错。

**为什么。**以后需要知道某次训练用了旧分析还是新分析，也要能比较修改前后的效果。修改prompt或模型后，程序还可能从缓存里取回旧caption；必须在开始重新标注前就使用新版本和新缓存目录。

- **输入：**原始QA、视频、旧标注以及已有训练题ID。
- **输出：**本批来源清单、新工作目录和新缓存目录；训练、验证、评测的视频分组记录。
- **失败怎么办：**视频找不到、题目ID重复、答案与题目配不上时先记录问题，停止该题后续处理。
- **比分题示例：**保留旧的“22:24分析”，新增修订版本，能查到二者来自同一个视频。

如果文件内容改变，可以用哈希检查。哈希可理解成文件的“内容指纹”：文件改变，指纹也会改变。后面批准的是一个具体版本的数据，不能拿批准旧版本的记录去训练另一份内容。

训练与评测应按视频分开。同一个视频的不同问题不应分到训练和评测两边。当前已经冻结的评测题和标签保持原协议，修订工作另存新版本。

### 9.4 第二步：确认删掉选项后，问题和答案仍然能看懂

**做什么。**检查开放题能否独立理解，并把正确答案写成明确的自然语言内容。

**为什么。**有的选项是完整答案，有的只是 `(a)(b)(c)` 或“以上都不是”。直接复制这些字符，不能自动得到合格的开放式监督。

- **输入：**原问题、全部选项、正确选项字母。
- **输出：**完整的开放问题、答案草稿，以及“从原选项提取/展开/人工修订”的来源记录。
- **失败怎么办：**缺事件字母映射、问题含糊、答案依赖已删除的选项时，记为“待复核”，补足依据后再继续。
- **比分题示例：**原问题本身完整，正确选项文字也是28 to 24，可以继续使用；这一步还没有证明28:24符合视频。

其他题需要额外处理：

| 原来是什么样 | 建议怎样处理 |
| --- | --- |
| 问题定义了(a)灯亮、(b)屏幕出现，答案是(a)(b) | 展开成“先灯亮，再出现屏幕”，保存原映射，防止展开顺序写反。 |
| `vwNurRWU`的答案是(a)(b)(c)(d)，问题却没有定义这些字母 | 根据原视频和原材料重新确认完整的键型、公式顺序，交审核者确认；不能猜字母含义。 |
| “下列哪个电话号码……”删掉选项后不完整 | 改成“画面提供的联系电话是多少？”，并核对改写是否保持原意。 |
| “None of the above” | 核查视频能提供什么答案；无法确定时保留合适的不确定回答，不能编一个具体答案。 |
| 音频题问“多少种声音” | 写清数的是声音种类，不能改成声音出现次数。 |

同样，不要把 `Hallucination` 题的 `I don't know` 自动当作坏标签。有些题就是检验模型会不会对没有证据的事情编答案。

### 9.5 第三步：复用已有时间戳 caption，核对并整理关键事实

**先说明与旧流程的关系。**这里确实包含“带时间戳的视频描述（caption）”这件事，旧标准 pipeline 已经做过，也保存了结果。前一版本节没有把复用关系写清楚，容易让人误以为需要新增一个从未做过的 caption 阶段。此次改进应从旧 caption 入手，补上关键事实核验、遗漏补查和结构化保存；不需要无差别地把全部视频重新描述一遍。

**已经找到的材料（2026-10-03 实际读取核对）：**

| 材料 | 实际内容 | 如何使用 |
| --- | --- | --- |
| [captions.jsonl](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/data/annotation/captions.jsonl) | 2,563 条缓存，对应2,563题、1,433个视频；每行含题ID、视频ID、caption、模型、采样参数和耗时 | 作为已有描述草稿，查找相关时间段。 |
| [traces.tar.gz](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/data/annotation/traces.tar.gz) | 32个分片文件，共3,172条题目trace；其中3,018题的bootstrap事件有caption文本（3,004生成、14复用） | 查明每题当时实际使用了什么描述，以及是否截断、格式检查是否通过。 |
| [export_worldsense_captions.py](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/training_code/scripts/export_worldsense_captions.py) | 已有JSONL转可读TXT的工具 | 方便逐段阅读缓存；它不会自动把trace中的额外caption补入缓存。 |

缓存条数与trace中的caption条数不同。当前缓存写入代码要求描述非空、通过格式校验、未截断；完整trace还会记录没有入缓存的生成结果。历史缓存写入和重启也需要按题核对，因此查某题当时实际使用的文本时，以该题trace为依据，不能只查缓存。没有caption文本的154题也不能直接判成“没有看视频”，还要看其survey和inspect记录。

旧caption是**针对题目生成的全片描述**：提示中含问题、选项和任务类型，要求重点描述相关时刻，但没有传入正确选项标签。它按`question_id`缓存，同一个视频的不同题可能有不同caption。生成阶段把画面、口播、字幕、音乐等写在同一时间段中；这些时间由模型生成，仍需与原媒体核对。

```text
旧流程：全片音视频 + 问题/选项
             ↓
        带时间戳caption（保存）
             ↓
        规划inspect → 查看片段 → 提交clue和observation

改进：读取该题旧caption和trace，保留原文与来源
             ↓
      拆出关键观察，标记时间、视觉/音频来源、待核验状态
             ↓
      回看对应画面/音频，补查缺失内容、纠正错误
             ↓
      保存核验后的事实 → 后续证据选择、独立回答与分析撰写
```

这里的caption负责描述视频；`clue_intervals`负责选证据时间；`observation`负责说明所选证据及理由。三者有关联，但不是同一个字段。

**做什么。**先从已有caption提取关键观察，再让标注模型或审核者回看相应音视频，按时间确认、修订并记录事实，暂时不写一大段解题分析。只对缺失、不完整、不适用或有疑点的部分补充生成；较大范围缺失时再分段重做。

**为什么。**“实际看到的东西”和“由此推出的结论”分开后，更容易发现错误。例如“47.5秒显示22:24”是真的，但“因此最终比分22:24”遗漏了后面的更新。

- **输入：**该题已有caption、trace、原视频、音频和完整问题。画面文字可以用OCR辅助，关键口播可以用ASR辅助。旧caption只是待核查材料；第9.7节的独立回答者仍不能看到它。
- **输出：**一张简单的事实表：时间、画面/声音中的内容、来自哪里、是否看得清/听得清。
- **失败怎么办：**看不清数字、听不清人名、caption被截断时重新看短片段或提高质量；仍无法确认就记“不确定”，转复核。
- **比分题示例：**写下两条事实，而不是只写一个“最终比分”。

| 时间 | 能直接确认的事实 | 由事实得出的结论 |
| --- | --- | --- |
| 47.5秒 | 比分图显示Texas 22、Maryland 24 | 此时是22:24。 |
| 48.25～48.6秒 | 比分图已显示Texas 28、Maryland 24 | 比分发生更新；视频末段可读比分为28:24。 |

一条事实最好能点开相应的帧或音频片段查看。对“她为什么生气”这类题，面部表情、原话属于观察；原因判断属于推断，不能把推断写成已经听见的原话。

caption是模型对全片的文字描述，它也会出错。如果格式检查失败，应先判断是否只是时间写法不同；如果描述真的不完整，再分段重新处理。程序应记录失败原因，不能因为模型写了一段长文字就视为事实全部确认。

**用同一道比分题看为什么还要核验。**旧缓存第174行就是`HuRReUbF::task1`，其`[00:00:36-00:00:49]`段落写道：

> The last clearly readable score state remains “23 TEXAS 22 MARYLAND 24 3rd 4:14,” indicating the post-touchdown total has not yet been refreshed before the clip ends.

意思是“最后可读比分仍为22:24，视频结束前没有刷新”。这条caption在trace（`s28.trace.jsonl`第9条）中恰好是`caption_valid=True`、`caption_truncated=False`。但本报告第9.2节的原视频抽帧已发现，48.25～48.6秒显示28:24。因此这题已经有时间戳caption、格式也通过了，仍需修正其中关于最后比分的事实。不能把“生成并保存caption”当作“内容已审核正确”。

拟新增的事实记录可以简单保存为：`题ID、开始/结束时间、观察内容、视觉/音频来源、对应帧或音频位置、核验状态、核验依据`。从旧caption拆出来时先标为“待核验”；只有实际核验后才能改成“确认”。原caption和修订记录分别保存，避免覆盖来源。

### 9.6 第四步：选证据，并检查实际保留下来的片段

**做什么。**从事实表中找出回答问题需要的画面/声音，再确定证据区间。程序修改区间后，要重新检查最终片段。

**为什么。**“有一段相关画面”和“这一段足够回答问题”不同。计数题可能需要每一次事件，顺序题需要全部相关事件，最终状态题要看到最后一次变化。

- **输入：**问题、关键事实、原视频和候选区间。
- **输出：**最终证据区间，以及它覆盖了哪些关键事实的说明。
- **失败怎么办：**缺一个计数事件、缺最终画面、区间修短后丢掉关键内容时重新选片段并复查；不能沿用修改前的通过记录。
- **比分题示例：**原46～48.715秒本来包含新比分，先确认末段画面被保留并且数字可读。此例不应简单归结为“区间必须更长”。

对于“最后显示”“最后发生”类问题，应显式检查末帧和最后一次状态变化。对于“全片有多少次掌声”，只看其中一次掌声的短片段不能证明总次数。

对于“某件事没有发生”，看一个短窗口也通常不够。必须说明查了哪些范围、是否可能漏掉；“暂时没有找到”不能直接等同于“全片没有”。

### 9.7 第五步：分两次核验，先独立回答，再检查观察说明

这里是两个不同任务，分开执行更容易理解。

#### A. 先不给标准答案，让核验者自己看视频回答

**输入：**完整开放问题和最终证据音视频。不给标准答案、旧caption、旧observation和旧对话。

**输出：**核验者自己的答案、它依据的时间段，以及看不清/听不清时的不确定说明。

下面是拟议的核验提示，**不是当前生产prompt**：

```text
只根据所提供的视频和音频回答：视频最后显示的比分是多少？
请给出你读到的比分和对应时间。
如果画面不足以确认最终比分，请明确说“无法确定”，不要猜。
```

这个核验请求里没有28:24，也没有原分析里的22:24。它应该自己查看最后的画面；若答28:24，程序保存这个结果，稍后再与原答案比较。

#### B. 再逐条检查候选事实是否有证据支持

**输入：**候选事实表和相应音视频。为了检查一句话，此时核验者当然需要看到这句待检查的事实。

**输出：**每条事实“有证据支持/被证据否定/暂时无法确认”，以及理由。

比分题中，可以同时得到：

- “47.5秒比分22:24”：有画面支持。
- “48.25秒比分28:24”：有画面支持。
- “视频最终比分22:24”：被更晚画面否定。

**失败怎么办。**两次核验产生分歧、返回无法解析的回答、API调用失败时，保存“不确定/检查未完成”，重试或交人工。程序不能把失败默认改成通过。

用同一个Qwen3.8模型开新会话，是让它重新独立做一次判断；它仍可能重复同一种错误。可以对风险题换一个支持音视频的模型再查，最终用人工抽检了解自动审核是否可靠。模型多次同意、自报confidence=1.0都不等于已经获得独立真值。

现有 `verify.py` 可作为部分基础，但它主要让模型**看单个片段、看选项、输出字母**，再统计是否有某段答对。新的开放题回答和逐事实审核还需要实现，不能把已有V1直接当成整套流程已完成。

### 9.8 第六步：核对事实、独立回答与数据集答案

**做什么。**把上一步的结果和原数据集参考答案放在一起，检查是否一致、哪里冲突。

**为什么。**既可能是标注模型看错，也可能是原题/原答案有问题。不能看到冲突后就把分析改成支持gold，也不能看到一个新模型答了另一个答案就自动改gold。

- **输入：**已核验的事实、独立回答、原参考答案。
- **输出：**“支持原答案”“需要复核”等判断，以及具体冲突点。
- **失败怎么办：**有冲突就暂停这一题，交人工查看原视频、音频和题意；需要改参考答案时保存原答案、修订理由和批准记录。
- **比分题示例：**更晚画面和独立回答都支持28:24，原参考也是28:24；应修正旧分析，保留原答案。

如果有另一道题，所有可靠证据都显示另一个结果，审核者才可能修订训练版本的参考答案。原benchmark的问题另行登记，正在运行的冻结评测标签不在这里自动改写。

### 9.9 第七步：从已确认的事实写简短分析，再做一致性检查

**做什么。**把已经通过核对的事实和答案交给分析生成器，让它写出学生能够使用的简短解题说明。

**为什么。**这里是在制作最终讲义。原定位说明里的“我再检查一下”“哪个选项比较接近”“可能是十一或十二”不应原样成为解题分析。

- **输入：**已审核事实、完整问题、经过核对的答案。
- **输出：**简短analysis和完整answer，以及它们所依据的事实记录。
- **失败怎么办：**出现新的无依据事实、分析/答案冲突、未完成计划或过长文本时，重新生成或交复核；没有解决就不通过。
- **比分题示例：**生成器此时可以看到核对后的28:24，因为前面已经检查了这个答案的依据。

拟议的生成要求可以写成：

```text
已确认：47.5秒比分为22:24，48.25～48.6秒更新为28:24。
已核对答案：28 to 24.
请只根据上述已确认事实，写简短英文分析和最终答案。
不要添加新的数字或场景，不要提选项和inspect工具。
如果事实不足以支持答案，请指出冲突，不要编解释。
```

根据这些已核实事实，本报告编写的**拟议修订目标**为：

```text
<analysis>
The score graphic shows Texas 22 and Maryland 24 at 47.5 seconds.
It updates to Texas 28 and Maryland 24 near the end of the video.
The last readable score is therefore 28 to 24.
</analysis>
<answer>28 to 24.</answer>
```

这与“把分析中的22直接替换成28”不同：它保留了真实的更新过程，并说明为什么最终采用后一个数字。

随后应检查分析里的数量、人物、左右、旋向、顺序和最终状态，确认能支持answer。**只检查“分析与gold一致”仍不够**，还要确认分析里的事实来自已经看过并核实的音视频。

建议分析通常写60～100个英文词，最多120词。120个词不等于120个token：一个英文单词可能被分成多个token。因此还要用Qwen实际分词器检查“分析+答案+标签”是否装得下512token。超长时重新摘要已确认事实，再检查摘要；完整原说明另存，不能直接截掉尾部。

### 9.10 第八步：逐题自动审核，批次人工抽检，最后决定能否训练

**自动部分。**每一道题都必须有必要检查结果：题目可理解、关键事实可核查、证据足够、答案得到支持、分析与答案一致、格式和长度合格。

**人工部分。**人工有两类工作，安排方式不同：

1. **处理疑难题。**先看本次23条分析/答案冲突、2条分析内部冲突和1条缺映射，再增加计数、音频、最终状态等风险题，形成约100题诊断样本。它们用来发现错误原因，不能用错误比例代表全体。
2. **抽查准备放行的题。**从自动检查通过的候选中随机抽约200题，覆盖不同题型、时长和模态，记录怎样抽出来的。它们用来检查自动审核有没有漏掉系统性错误。

这里不要求每一道题都人工看完。它要求**每道题都有必要的自动核验记录，整批有人工抽检；发现分歧的题单独人工处理**。抽检尚未通过时，整批也不能当作已审核完成。

审核者先只看题目和原视频/音频，记下自己的判断，再看gold、旧说明和新分析。关键风险题和放行抽检建议由两人审；意见不同再交负责人或第三人处理。保存谁审的、审了哪一版、为什么通过或修改。

每题使用以下状态，状态名称就是程序以后读取的判断：

| 状态 | 含义 | 是否进入正式训练 |
| --- | --- | --- |
| 尚未完成检查 `pending` | 还缺必要的核验结果；这是新流程开始时的默认状态。 | 否 |
| 待复核 `review` | 有分歧、缺映射、关键事实不清，需要补查。 | 否 |
| 审核通过 `accepted` | 该版本必要检查通过，并满足所属批次的人工抽检要求。 | 可以进入训练候选 |
| 无法使用 `quarantine` | 媒体损坏或题目无法适配当前任务等，暂时没有可用处理办法。 | 否 |

现有1,453条开始时都设为pending，意思是“还没有完成这套新检查”，不是“全部已经发现错误”，也不是“全部必须逐题人工审核”。大部分可先走独立自动音视频检查；冲突或不确定的题转到review交人工补查，自动检查通过的题再接受所属批次的随机人工抽检。pending是流程中的未完成状态，review则是已经发现具体疑点的待复核状态；二者都不能作为accepted导出。

可以修好的缺映射或分析冲突应先放“待复核”，不要直接扔掉。仅仅“程序没有查出文本错误”也不能标为accepted，因为它还没有核对视频事实。

初次试运行可把人工抽检的事实支持率≥95%设为目标，发现关键逻辑冲突时回查同类问题。95%是建议的试运行要求，不是当前数据已有的质量结果；它也不意味着允许已知有冲突的单条样本进入训练。

### 9.11 第九步：质量通过后，再检查这道题对CLUE训练是否有用

这一步复用Full/Gold思路：让冻结模型看完整视频回答，再看证据片段回答，比较是否有帮助。

- **输入：**审核通过的题，以及与实际训练一致的媒体预算。
- **输出：**Full/Gold结果、Tier分类、准备选入训练的题目清单。
- **失败怎么办：**模型答错先记录，结合其他结果判断训练价值；不能自动宣布“标签错误”。运行失败则补跑，不能用缺失结果代替成功。
- **比分题示例：**审核已经确认答案28:24正确。7B如果仍然读错，只能说明它这次没正确使用证据，不能推翻已经核实的末段画面。

**质量与效用是两张不同的成绩单：**

| 判断 | 它要解决什么问题 |
| --- | --- |
| 质量审核 | 这份讲义的事实、问题、分析和答案是否可靠？ |
| Full/Gold效用筛选 | 这份可靠证据是否能让当前teacher比看整片更容易回答？ |

Tier A/B/D不能代替accepted。本次560条Full/Gold都答错的样本需要进一步核查，不能一键删成“560条错标”。反过来，HuRReUbF的Gold答对也没有证明它的旧分析正确。

还需要单独看**训练给学生的帧和音频里能不能找到所需信息**。标注者高清看到一个小数字，学生的输入可能把它缩得难以辨认。这是输入信息是否可用的检查，不等于要求当前Full学生已经答对；学生还不会用可见证据，正是训练可能帮助的地方。

最后，SFT和CLUE应从同一份已审核的分析/答案记录导出。若分析不能修好，但题目与答案已独立确认，可另建清楚标记的answer-only实验；未解决的矛盾不应靠降低权重继续进入本次分析监督。

## 10. 怎样落地：先写哪些程序，文件怎样串起来

**以下脚本名是建议的开发拆分，当前并未新增这些生产脚本。**本次任务B已有的是调查用脚本和风险清单；这节说明以后如何把方案变成可执行流程。

为了容易理解，把程序分成三组：先做不需要调用标注API的整理，再加音视频核验，最后做训练导出。每组先在小批题目上检查，再扩展规模。

### 10.1 第一组：建立新版本，整理现有1,453题的检查清单

这一组优先开发。它不需要新模型回答，主要读现有文件、整理问题和记录来源。

| 建议脚本名 | 读什么 | 做什么、写出什么 |
| --- | --- | --- |
| `worldsense_annotation_v2_entry.py` | 原QA、标注、视频位置、训练题ID | 创建新工作目录和新caption/clip缓存目录，保存本批来源及参数；后面各程序从这里拿同一批题。 |
| `import_worldsense_caption_candidates_v2.py`（拟新增） | 旧`captions.jsonl`和完整trace | 按题关联实际使用的caption，保留原文、来源、格式/截断状态；写`caption_candidates.jsonl`，全部作为待核验材料，不冒充新版本已通过的缓存。 |
| `audit_worldsense_annotations_v2.py` | 现有observation、答案、区间、trace | 检查文本冲突、事件代码、超长、截断等，写“检查结果表”和“待复核题清单”；全部题初始仍是未完成审核。 |
| `normalize_worldsense_openqa_v2.py` | 原问题、原选项、正确选项和检查结果 | 展开有明确映射的事件代码，形成完整开放问题/答案草稿；没有映射就保留待复核原因。 |

JSONL是后续可能采用的保存格式，可以理解成“每行保存一道题及相关信息”。新手只需先理解下面这些文件各自负责什么：

```text
原QA + 旧标注 + 现有训练题ID
              ↓ 新版本入口
来源清单、新工作目录、新缓存目录
              ↓ 静态检查程序
checks.jsonl：发现了哪些问题、还缺哪些检查
              ↓ 开放题整理程序
open_questions.jsonl：完整问题、答案草稿、改写依据
```

**`open_questions.jsonl`还不是训练文件。**它只是整理后的题目草稿。静态检查能发现“11与13冲突”，却无法仅看文字确定视频里到底有11个还是13个。

现有任务B的 `audit_annotation_quality.py`、`flagged_annotations.jsonl` 和35题文本复查可以提供第一批检查结果。不能把“没有出现在风险清单里”的其他题直接标为审核通过。

版本和缓存必须在开始重标前处理。最简单的初版做法是每次正式修订使用新的工作目录和缓存目录，并把它们明确传给现有标注入口；以后再把模型、prompt、视频和QA的内容指纹加入缓存键。否则换了新prompt，程序可能仍复用旧caption和旧submitted结果。新缓存与复用旧描述不冲突：旧caption通过上述导入步骤明确作为候选材料保存，新生成/已核验的记录另存，并保留二者关联；不必为了隔离缓存而全部重新生成。

### 10.2 第二组：确认音视频事实，生成可审核的分析

这一组才涉及新的模型调用和视频检查。初次建议用约100题风险样本试运行，先查出错误机制和每题成本。

| 建议脚本名 | 读什么 | 做什么、写出什么 |
| --- | --- | --- |
| `reannotate_worldsense_evidence_v2.py` | 开放问题、旧caption候选、原视频、待复核原因 | 复用已有API/切片框架，从旧描述提取候选事实，回看片段核对并按需补充生成、选证据；写`evidence_checks.jsonl`，保存实际片段来源和处理参数。 |
| `verify_worldsense_annotations_v2.py` | 问题、最终片段、候选事实 | 先不看gold独立回答；再逐事实看证据；写`independent_checks.jsonl`，保留分歧和失败。 |
| `write_worldsense_training_analysis_v2.py` | 已核验事实、问题、核对后的答案 | 生成短analysis/answer，再检查是否互相冲突或添加新事实；写`analysis_candidates.jsonl`。 |

这些程序的关系是：

```text
open_questions.jsonl + 原视频
                 ↓ 重看证据
evidence_checks.jsonl：看到/听到哪些事实，证据在哪里
                 ↓ 独立核验
independent_checks.jsonl：自己的回答、事实核查、分歧
                 ↓ 核对参考答案；有冲突转人工
analysis_candidates.jsonl：拟采用的简短分析和最终答案
```

比分题的实际内容会这样流转：

1. 原说明“最终22:24”被检查程序标成与答案28:24冲突。
2. 重看末段，记录47.5秒22:24、48.25秒后28:24。
3. 独立核验者不给gold也读出28:24；事实检查否定“最终22:24”。
4. 核对原答案，确认这次应修分析。
5. 生成第9.9节展示的短分析和答案草稿，等待最终审核。

可复用的旧代码与需要补的功能要分清：

| 现有文件 | 已有能力 | 还需要补什么 |
| --- | --- | --- |
| `api_client.py`、`prompts.py` | 调API、生成caption、重试和规划 | 时间格式兼容、真正失败的分流；事实与推断分开保存；不同任务使用不同核验提示。 |
| `clips.py` | 切片、转码、回退、检查音轨 | 将最终实际尺寸/fps/片段指纹等写回审核记录，方便查模型拿到的材料。 |
| `episode.py` | inspect/submit和区间修正 | 实质修改区间后重新检查最终片段；submitted不能直接当accepted。 |
| `verify.py` | 单片段选择题验证 | 完整开放回答、多个区间共同核验、逐事实审核，以及明确的不确定/错误状态。 |

无须一开始为所有题加ASR/OCR和多模型投票。可先针对数字、小字、人名、声音计数、最终状态等风险任务加相应辅助工具。模型输出仍需证据核查，不能仅因多次答案一致就批准。

### 10.3 第三组：记录审核决定，统一导出SFT和CLUE

| 建议脚本名 | 读什么 | 做什么、写出什么 |
| --- | --- | --- |
| `decide_worldsense_annotation_quality_v2.py` | 前面所有检查结果、人工意见、批次抽检结果 | 逐题决定pending/review/accepted/quarantine，写`review_decisions.jsonl`；保存是谁/哪个程序审了哪一版以及理由。 |
| `export_worldsense_verified_training_v2.py` | 审核决定、完整开放问题、已审核分析/答案、证据区间 | 只导出同一版本的accepted题，生成新的SFT/CLUE训练文件和导出清单。 |

旧人工审核网站可以继续用来展示视频，但需要将它保存的意见与题目、标注版本和各项检查关联。人点一个“good”，程序还要知道审的是哪一版、哪段证据、哪份分析。

这份共同的审核记录应同时供SFT和CLUE使用：

```text
analysis_candidates.jsonl + 自动核验结果 + 人工记录
                         ↓ 审核决定程序
review_decisions.jsonl + 已审核分析/答案
                         ↓ 同一个导出入口
             ┌───────────┴────────────┐
             ↓                        ↓
     sft_verified.jsonl       clue_verified.jsonl
     学生：完整视频+问题       学生：完整视频+问题
     目标：审核分析+答案       教师：审核证据+答案
                              按实验设置加入审核分析
```

**为什么要共用一份审核分析。**如果SFT导出时自己清洗一次、CLUE导出时又另洗一次，两边可能得到不同的监督内容；出现问题后也难以追踪。审核通过后应固定这一版，两个训练分支消费同一份内容。

对现有两个加工脚本，需要改变它们读取的依据：

- `prepare_worldsense_observation_sft.py` 现在主要检查submitted和非空，然后直接把observation放进analysis。以后应读取**已审核分析和accepted决定**，不能继续直接拼原observation。
- `add_worldsense_teacher_observation.py` 现在检查两份数据的gold文字相同，再把SFT分析加进teacher prompt。这个“文字相同”不证明答案正确；prompt里写“verified correct answer”也只是提示措辞。以后应同样检查审核决定和数据版本，再加入已经确认的辅助分析。

### 10.4 程序怎样实际阻止有问题的数据进入训练

导出程序不能只看“某个模型说通过”。应逐题检查以下条件：

1. 这道题有完整的审核记录，不是pending或review。
2. 必要的事实、答案、一致性检查完成；API失败、看不清或解析失败仍算未完成。
3. 本批要求的人工抽检已完成并达到约定标准，疑难题分歧已处理。
4. 审批记录对应当前题目、答案、分析和证据的版本及内容指纹。

只有满足条件的accepted题才能写入新的训练文件。

例如当前有1,453题，审核后只有1,200题满足条件，就先输出1,200题，并明确列出其余253题为什么未通过。**这里的1,200/253是说明程序行为的假设数字，不是本次调查结果。**程序不能为了满足“要1.5k条”，把待复核题补回训练集。

开始训练前，再检查启动脚本的数据路径确实指向这份新训练文件，并核对导出清单。否则，审核程序虽然写好了新文件，启动脚本仍读取旧SFT文件，修改就没有进入训练。

一旦以后改了问题、答案、分析或证据区间，应重新检查受影响的部分，更新批准记录。不能把“这道题ID以前通过过”当成所有新版本都通过。

### 10.5 哪些工作现在可以先做，哪些需要API或人工

| 工作 | 需要新的标注API调用吗 | 需要人工吗 | 注意事项 |
| --- | --- | --- | --- |
| 建立新目录/版本、对齐ID、保存来源 | 不需要 | 一般不需要逐题人工 | 必须在重新标注前做。 |
| 查明确文字冲突、残留代码、长度、格式 | 不需要 | 确认语义边界时需要 | 自动结果是风险清单，不是事实真值。 |
| 展开原问题已定义的事件代码 | 不需要 | 抽查展开是否正确 | 缺定义的题不能靠字符替换解决。 |
| 本地抽帧、截取音频、展示证据 | 不需要 | 看/听这些证据通常需要 | 有条件也可接本地识别模型，但模型识别仍可能出错。 |
| 重写caption、补定位、独立音视频核验 | 使用云模型时需要 | 分歧和抽检需要 | 可以另选合适本地模型；不把文本裁判当音视频核验。 |
| 生成新的短分析、做语义审核 | 使用云模型时需要 | 疑难题需要 | 可以接已有本地文本模型，但它不能替代源视频检查。 |
| 风险题处理、放行抽检、原gold冲突处理 | 不一定需要API | 需要 | 要保存实际审核者和版本；助手抽帧阅读与人工全片审核分开记录。 |
| 根据审核清单导出新训练数据 | 不需要 | 通常由程序执行 | 必须检查accepted、版本、必要结果和批次抽检要求。 |

**建议实际开发顺序：**

1. 先完成第10.1节，使用新目录，整理现有问题；此时不批准任何尚缺音视频核验的题。
2. 搭建第10.2～10.3节的最小流程，在约100题风险样本上跑通“看证据→独立核验→短分析→审核决定”。
3. 用人工检查这个流程能否识别比分更新、旋向冲突、缺映射，又能否正确保留相容描述。
4. 自动审核达到可用水平后扩大到训练候选，完成批次人工抽检，生成已审核候选清单；这时还不导出正式训练文件。
5. 对合格候选做Full/Gold效用筛选，再正式导出SFT/CLUE训练文件，最后做小规模训练对照。SFT也可以按实验方案选样而不依赖Full/Gold，但比较SFT与CLUE时应冻结相同的训练题ID。标注正确性、训练效用与最终模型效果分别记录。

本次交付完成了问题调查和这些步骤的说明。生产流程、付费调用和新训练均应按后续确定的方案执行；当前正在进行的评测继续使用已经冻结的数据。

## 11. 实施顺序与验证改进是否有效

### 11.1 第一阶段：现有1,453条的无API整理

### 13.2 当前究竟由哪个模型核验？

**实际请求记录中的模型名是 `qwen3.8-omni-flash`，temperature=0。**事实整理、疑点分级、片段复核、clue盲答、observation写作和最终审计都调用同一个模型，通过不同提示词承担不同角色。

这与训练中的Qwen2.5-Omni-7B student/teacher是两件事。本次核验也没有额外使用另一个独立模型做裁判或投票。所谓“独立盲答”指**新请求、输入隔离、不向该请求提供标准答案或先前分析**，不表示使用了另一种模型。

每个阶段都新建对话。模型不会自动记住上一请求；脚本显式放入的`previous_feedback`才是它能看到的历史反馈。提示、原始回复、媒体参数、格式错误、解析结果均保存在每题的`requests/*.json`中。

### 13.3 当前一次重标是怎样走完的？

```text
完整原视频+音频、问题选项、旧caption草稿、上一轮反馈
    ↓
生成带时间戳的事实、推断、新clue区间、不确定事项
    ↓
如有疑点：另一次全片请求，判断是否影响选答案/事实成立
    ├─ 附带疑点：保留记录，继续
    └─ 关键疑点：模型提出复核区间
                  →脚本生成短AV片段→模型复查
                  →回到全片上下文更新事实与疑点
    ↓ 若关键疑点已解决
只给最终clue音视频+问题选项，进行独立盲答
    ↓ 字母与标准答案一致
给最终clue、候选事实和标准答案，写≤120英文词的observation
    ↓ 如写作还报告疑点，先做一次全片疑点核验
给完整原视频、标准答案和新observation，做逐声明审计
    ↓ 双项通过
导出自动核验候选；否则有剩余轮次就带反馈重试
```

| 阶段 | 音视频输入 | 显式给标准答案吗？ | 主要输出/判断 |
| --- | --- | --- | --- |
| 全片事实整理 | 完整原音视频 | 不单独注入`golden_answer`字段；但旧草稿/反馈可能包含此前的答案相关文字 | 事实、推断、clue、不确定事项 |
| 疑点分级 | 完整原音视频 | 不单独注入标准答案；候选observation可能来自此前含gold的写作 | 每条疑点是否影响选答案/事实支持、原因、复核范围 |
| 针对性复核 | 所选范围；每请求不超过60秒，较长范围完整拆分 | 不单独注入标准答案；携带具体疑点及其分类 | 更具体的证据、剩余不确定性、时间映射 |
| **clue盲答** | 所有最终clue区间取时间并集后顺序拼接，保留同步音频 | **不给gold、caption、observation、候选事实、上一轮反馈** | 选项字母或`UNKNOWN`、证据、理由；由程序与gold比较 |
| observation写作 | 最终clue音视频 | **给标准字母及对应选项文本** | ≤120英文词的observation及疑点 |
| 最终observation审计 | **完整原视频及音频** | **给标准答案、候选observation和clue区间** | 逐声明PASS/FAIL/UNKNOWN，以及整体一致性 |

最终审计检查：observation是否符合音视频、是否与gold相容、gold是否有音视频支持、clue是否足以支持答案。所有必要声明和全局判定需要通过；`FAIL`或`UNKNOWN`不放行。

音视频限制也应与判断能力分开理解：全片默认优先2fps及640×360像素面积，短段优先4fps及1280×720像素面积，但不超过原视频尺寸；7MB内联文件预算可能触发降采样。实际参数记录在请求中，不能把请求编码帧率直接当作云端模型实际看过的帧率。

### 13.4 失败后，会把原因一起发回去让 Qwen3.8-Omni-Flash 改吗？

**会，但目前是“把结构化反馈发给下一轮事实整理”，而不是“将完整失败记录直接交给同一段持续对话里的模型改observation”。**

实现位于 [quality_gate_v2.py](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/training_code/src/omni_opsd/worldsense/quality_gate_v2.py) 的`feedback()`和`process_item()`：下一轮全片事实请求的`DATA.previous_feedback`会包含这些信息（存在时）：

| 字段 | 通俗含义 |
| --- | --- |
| `failure_category` | 上一轮在哪一步失败 |
| `proposal` | 上一版事实、新clue与不确定事项 |
| `uncertainty_review` | 每条疑点的关键/附带分类及理由 |
| `focused_recheck` | 更仔细查看片段后发现了什么 |
| `draft` | 上一版observation和写作疑点 |
| `previous_blind_evidence` / `previous_blind_reason` | 上一次盲答引用了哪些证据、为什么这么答 |
| `rejected_observation_claims` | 最终审计中未通过的具体声明、时间、判定和证据说明 |
| `write_uncertainty_review` | 在observation写作后被拦截时，额外携带该次疑点核验详情 |

这些反馈确实出现在保存的API请求中。例如平板题`KzOiyMSp::task0`第2轮事实请求带有如下内容（节选意译）：

```text
失败声明：42–49秒，擦除后写下“H 2”。
判定：FAIL。
理由：所见更像“H”后一个竖线，无法明确支持“2”。
```

因此，不能说模型完全没有收到纠错原因。但仍有几个具体不足：

1. **反馈主要到事实整理，未完整直达下一轮写作者。**后续写作请求主要接收新事实、片段映射、疑点分类和gold，没有直接附上上一版observation与失败声明清单。事实整理未消化的错误可能再次出现。
2. **未完整传递最终审计的全局解释。**`feedback()`会提取未通过的声明，但没有直接传递整个`observation_audit.reason`及全部全局判定。若各声明都PASS、只有整体gold判定FAIL，`rejected_observation_claims`可能为空。领导人关系题恰好暴露这种判决自相矛盾的风险；它发生在第2轮，实际没有第3轮继续修改。
3. **阶段间并非全部严格盲化。**为纠错而传回的draft或失败声明可能提到参考答案内容。只有clue盲答请求通过字段白名单严格隔离这些材料，不能把整个重标过程称为“完全不看gold”。
4. **两轮预算不等于无限改到通过。**第1轮语义失败才会进入第2轮；第2轮仍失败就保存`needs_review`。这两轮指本次v2重跑，不包括旧试跑的历史尝试。JSON格式/截断错误的同阶段最多两次生成属于另一种技术重试。
5. **重试不保证增加新证据。**当前17题中有12题两轮clue区间完全相同，10题两轮盲答请求哈希完全相同。需要把“有反馈”进一步落实为“根据失败类型改变取证或检查方法”。

### 13.5 当前是否仍是之前脚本的 agentic 过程？

2026-10-04 补充：[三个两轮盲答失败案例与可播放 demo](WORLDSENSE_AGENTIC_CASES_AND_DEMO_20261004.zh-CN.md)。该文逐步对照蛋挞计数、说话人识别、提示音计数的历史 inspect 轨迹与本次两轮记录，并区分实际执行和建议修复步骤。

**没有直接复用旧版`run_episode()`的 agentic 工具循环。当前是脚本控制步骤的、有界的多阶段核验与修订流程；其中模型仍会提出clue和复核区间，脚本据此取证。**

这里的 agentic 可以简单理解为：模型看到当前信息后，自主决定下一步调用哪个工具、查看哪一段，收到结果后再决定继续查看还是提交。

| 对比项 | 历史 agentic 标注 | 本次50题试跑 / 23题重跑 |
| --- | --- | --- |
| 主入口 | `annotate_worldsense_evidence.py` → `runner.py` → `episode.run_episode()` | `run_worldsense_quality_pilot.py` / `rerun_worldsense_uncertain23.py` → `quality_gate.py` / `quality_gate_v2.py` |
| 下一步由谁决定 | 模型输出JSON action；程序校验和执行 | 程序按阶段、PASS/FAIL、疑点类别决定下一步 |
| 模型可提出的动作 | `get_media_info`、`inspect`、`submit` | 返回事实、clue区间、疑点分类、focus区间、核验结果；没有旧版action循环 |
| 查看方式 | `inspect`可提出起止时间、fps、像素预算、模态等；程序限制预算和重复查看 | 模型提出时间区间，脚本决定编码参数、拼接、超长拆分，并调用固定的复核提示 |
| 上下文 | 同一题的`messages`持续追加模型动作和媒体结果；旧媒体视图会受上下文保留预算限制 | 每阶段新建请求；历史信息由结构化字段显式传入 |
| caption | API后端可先生成/复用时间戳caption，交给模型规划inspect | 复用已有caption作为未核验草稿，再生成结构化事实；没有调用旧`bootstrap()`开始一轮agent |
| 何时结束 | 模型`submit`，或达到工具/轮数预算 | 双重核验通过，或用完重标轮次进入待复核/技术失败 |
| 通过标准 | 原定位循环的提交主要检查协议、区间和预算，不等于独立语义核验通过 | clue盲答与observation核验成为本次候选导出的条件 |

代码层面的关键区别：旧版 [episode.py](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/training_code/src/omni_opsd/worldsense/episode.py:397) 在循环中把`inspect`结果加入同一`messages`；新版 [quality_gate.py](/opt/huawei/dataset/hyl_ulan/ylhu/omni-clue-opsd/training_code/src/omni_opsd/worldsense/quality_gate.py:294) 的`ReviewAPI.call()`每次构造新的用户消息，再调用同一个`QwenAPIOmniClient._generate_text()`。**复用了API客户端，不等于复用了旧agent的规划和工具调用逻辑。**

### 13.6 现有实现与下一步建议要分开

已实现并运行：疑点分级、片段复核、具体失败反馈、超长复核区间无遗漏拆分、最多两轮重标、最终双重核验；相关测试33项通过。23题重跑新增6题通过，原50题合并后29条候选，人工审核数量仍为0。

尚需改进：

1. 给observation写作者直接提供上一版文本、失败声明和修改要求，再审计修改后的每个声明。
2. 对最终判决增加标准答案映射与逻辑自洽检查；核验器自身出错应进入判决复核。
3. 将合法未知选项落实为结构化路由，而不仅是在提示里解释。
4. 按计数、说话人、状态变化、复合选项选择取证方法；相同请求不应反复调用充当新证据。
5. 若接回旧agent，应把失败证据交给受预算约束的`inspect`修复循环，再将其提交结果交给隔离的盲答和observation核验；不能仅因agent主动`submit`就认定质量合格。
